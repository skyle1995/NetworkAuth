## 〇、先看这部分：什么在全局，什么按应用

一号通的分界线只有一条：**产生或消耗「全局资源」的配置归全局，决定「这个应用怎么被使用」的配置归应用。**

### 全局一套（`settings` 表 + 独立管理页）

| 资源 | 说明 |
|---|---|
| 账号 | `members` 一行一个账号，`username` / `email` 全站唯一 |
| 钱包 | `expired_at`（到期时间）、`points`（点数）、`total_recharge`（累充）**所有应用共享同一份** |
| 会员等级 | `member_levels` 全站一套，按累充自动升级 |
| 卡密 | `cards` 全站卡池，任意卡可在任意应用登录/充值 |
| 卡密套餐 | `card_packages` 全站一套，制卡时快照进卡 |
| 接口定义 | `apis` 每个 `api_type` 恰好一条，27 条全站启用 |
| 账号策略 | 注册 / 邮箱验证 / 卡密注册 / 卡密登录 / 卡密充值 / 试用 / 注册限制（见第六章） |
| 黑名单 | `blacklists` 按设备/IP/地区，全站生效 |

### 按应用（`apps` 表）

| 配置 | 说明 |
|---|---|
| 应用身份 | `uuid` + `secret`（secret 是唯一身份凭据，请求签名用） |
| 内容分发 | 版本、更新方式、下载地址、公告、公共数据 |
| 会话策略 | 心跳间隔、自动离线、清理间隔 |
| 满员策略 | 账号在线名额满时，进入本应用怎么处理 |
| 绑定验证 | 机器码 / IP 验证与转绑全套参数 |
| **计费策略** | 三种模式 + 要求等级 + 点数消耗（见第一章） |

> ⚠️ **钱包共享的直接后果**：用户在 A 应用花掉的点数，B 应用立刻看得到余额减少；在 A 买的时长，B 也认为账号有效。这是「一号通」的定义，不是 bug。

## 一、计费策略（按应用）

账号只有一份钱包，但**怎么花由应用决定**。`free_mode` + `billing_mode` + `required_level` 三个字段决定门禁，`points_*` 系列决定扣费。

### 1.0 三模式总览

| 模式 | `billing_mode` | 门禁条件 | 扣费 |
|---|---|---|---|
| **计时模式** | `0` | 账号有效（未到期/永久）**且** 权限等级 ≥ `required_level` | 不扣点 |
| **点数模式** | `1` | 点数足够 | 每次登录扣 `points_per_login`（或按周期扣） |
| **高级模式** | `2` | 等级 ≥ `required_level` **且** 点数足够 | 按**该等级在本应用配置的点数**扣 |

**计费豁免** `free_mode=1`：跳过全部门禁与扣费（不看等级、不看到期、不扣点）。凌驾于三模式之上。

| `free_mode` | 说明 |
|---|---|
| `0`（默认） | 正常计费，按 `billing_mode` 走 |
| `1` | 该应用完全免费。已充值的时长/点数**原样保留但不消耗**；转绑不扣费；功能扣点接口报「当前非点数计费模式」 |

> ⚠️ **`required_level=1` 等价于「不限等级」**。因此「计时模式 + 要求等级 1」就是传统意义上的免费应用（只要账号没过期）。
> ⚠️ **计时模式会校验到期时间，点数/高级模式不会**。这意味着时长到期的账号仍可在点数应用里继续用点数消费——这是有意设计，让两个钱包都能单独起作用。

### 1.1 计时模式（`billing_mode=0`）

- 账号 `expired_at` 未到期即可用；`permanent=true`（到期=2099 年）为永久，永不到期、扣时无效。
- 权限等级（`member_levels.level`，无等级账号为 1）须 ≥ `required_level`，否则报「会员等级不足，需要 XXX 及以上」。
- 登录/心跳发现已到期 → 返回「账号已到期」。
- 充值（`22`）、领试用（`24`）在当前到期时间基础上**顺延分钟数**。
- 客户端应展示 `expired_at` + `level` / `level_name` / `level_color` 作为「会员状态」。

### 1.2 点数模式（`billing_mode=1`）

只看 `points` 余额，不看到期时间。`points_charge_mode` 决定扣费方式：

#### 按次（`points_charge_mode=0`）

- 每次登录扣 `points_per_login` 点；**`0` = 登录不扣**（点数仅由 `53 功能扣点` 显式消耗）。
- 余额不足登录被拒。登录成功后会话内不再以点数拦截。

#### 按时（`points_charge_mode=1`）

- 每 `points_period_minutes` 分钟扣 `points_per_period` 点（周期最小 1 分钟、每周期扣点最小 1）。
- 结算时机由 `points_heartbeat_charge`（「扣费触发」）决定：

  | 扣费触发 | 值 | 登录时 | 心跳时 |
  |---|---|---|---|
  | 登录预扣 | `0` | 立即扣 1 个周期并顺延 | 到期后自动续扣下一周期 |
  | 心跳触发 | `1` | **不扣** | 首个周期延到首次心跳时扣 |

- **心跳按周期扣费**：是否扣费完全由应用配置决定，客户端**没有参数可干预**。
  - 离线不补扣：跨过多个周期只按「当前时间」重新起算一个周期，不追扣欠费。

### 1.3 高级模式（`billing_mode=2`）

同时要求**等级达标**和**点数足够**，且点数按等级差异化。

**配置路径**：应用列表「更多 → 等级点数」，逐个等级填该应用的点数消耗。

| 情况 | 扣多少 |
|---|---|
| 该等级已配置 | 用配置值（按次=每次登录，按时=每周期） |
| 该等级未配置 | 回退到应用上的 `points_per_login` / `points_per_period` |

实现细节：配置存在 `app_level_points` 表，唯一键 `(app_uuid, member_level_uuid)`；加载后按等级 UUID 建快照查询。

> ⚠️ **「已配置为 0」与「未配置」不同**：配置 0 表示该等级在该应用**不扣点**（但仍需等级达标）；未配置才回退默认值。
> 典型用法：等级越高点数越便宜（白银 10 点、黄金 5 点、钻石 0 点）。

### 1.4 卡密与试用发什么，不再看模式

一号通把「发什么」和「怎么收费」解耦了：

| 卡面值 | 发放 |
|---|---|
| `points > 0` | 累加到账号点数 |
| `duration ≠ 0` | 累加到账号到期时间（`-1`=永久） |
| 两者都有 | **两边都发** |

试用同理：`account_trial_points` 与 `account_trial_duration_minutes` 各自独立配置，都为 0 视为未开启试用。

> 旧版「时长模式发时长、点数模式发点数」的二选一逻辑已移除。一张卡可同时卖「30 天 + 500 点」。

## 二、登录与在线策略

| 设置 | 字段 | 取值 | 逻辑 |
|---|---|---|---|
| 满员策略 | `login_type` | 0 顶号 / 1 非顶号 / 2 手动顶号 | 账号的「同时在线」名额满了以后，进入**本应用**时怎么处理：**顶号**=踢掉最早那台设备（该设备上的全部激活一起下线）；**非顶号**=拒绝，返回「已达最大同时在线数」；**手动顶号**=返回在线设备列表（`code=3` + `sessions`），客户端弹窗让用户选一台踢掉再重试 |
| 清理间隔 | `clean_interval` | 小时（默认1） | 后台清理任务对**该应用**的运行周期（基础节拍 1 分钟，按此值决定隔多久真正扫一次失效会话） |
| 心跳间隔 | `check_interval` | 分钟（默认10） | 登录后随 `heartbeat_interval` 返回给客户端，告知其多久心跳一次（不配置回退 10） |
| 自动离线 | `offline_timeout` | 分钟（默认30） | 超过该时长未心跳 → 会话判失效（登录时清理 + 后台扫描删除；不配置回退 30） |

> ⚠️ **三个时间字段关系**：后端强制 `自动离线 ≥ 心跳间隔`，否则客户端还没来得及心跳就被判离线。

> **「多开数量」「多开范围」已不在应用上配置**：在线名额与设备白名单都是**账号级**资源
> （见后文「全局账号策略」的账号资源配额），不按应用重复计算。
> 同一台电脑上开 3 个插件只占 1 个在线名额。

## 三、机器码 / IP 绑定与验证

绑定与转绑的开关、额度全部在**账号策略**里配置（见第六章 6.5）。
`bindings` 表无 `app_uuid`：一个账号在所有应用共用同一批绑定记录。

应用侧只保留一个「满员策略」（`login_type`）：账号的在线名额满了以后，
进入本应用是顶掉最早的、拒绝新的、还是让用户手动选。

> ⚠️ IP 验证绑定/校验的是**服务端识别的客户端 IP**：默认取 TCP 直连对端、不信任 `X-Forwarded-For`；
> 反向代理部署必须配置 `server.trusted_proxies` 白名单（见 README「反向代理与客户端 IP 识别」），
> 否则所有用户会被绑到同一个代理 IP 上。

## 四、卡密套餐与会员等级（全站）
这两类实体**不再归属应用**，全站一套（各有独立管理页）。

### 4.1 卡密套餐（制卡的售卖单元）

制卡不再手填时长/点数，改为**选套餐**——面值与售价由套餐决定，并在制卡时**快照进卡**（套餐后续改动不影响已售出的卡）。

| 字段 | 取值 | 逻辑 |
|---|---|---|
| 套餐名称 | 文本 | 如「月卡」「1000点」「30天+500点」 |
| 类型 | 0 时长 / 1 点数 | ⚠️ **仅用于分类与展示**，不再与应用计费模式绑定 |
| 面值时长 | 分钟，`-1`=永久 | 非 0 即发放到到期时间 |
| 面值点数 | ≥0 | >0 即发放到点数 |
| 售价 | 元（存储为整数**分**） | 累充升级的计量口径 |
| 状态 | 0 禁用 / 1 启用 | 禁用的套餐制卡时不可选 |

> **面值至少配置一项**（时长 ≠ 0 或 点数 > 0），否则制卡时被拒，避免制出废卡。
> 制卡链路：选套餐 → 快照 `duration/points/price` 进卡 → 核销时读卡自身字段。
> 卡密是全站卡池：不归属任何应用，也不记录发行渠道，任意卡可在任意应用核销。

### 4.2 会员等级（累充升级 + 充值返利）

账号按**累计充值金额**自动升级（只升不降）；权益为**充值返利**、**额外设备**、**额外并发**、**赠送免费换绑次数**，以及**高级模式下的点数折扣**。

| 字段 | 取值 | 逻辑 |
|---|---|---|
| 权限等级 | 整数 ≥1（**自定义**） | **数值越大权限越高**，随登录/心跳下发 `level`。应用的 `required_level` 与高级模式的点数配置都按它比较。配一个 `level=1` 的等级即可**给默认档命名/配色** |
| 显示颜色 | hex（如 `#E6A23C`） | 等级标识颜色，创建/编辑时用取色器选。**随登录/心跳下发 `level_color`**；默认档灰 `#909399` |
| 累充门槛 | 元（存整数**分**） | 累充达到即升到该等级 |
| 充值返利 | 0–100（%） | 充值时按比例多发面值。**先按充值前等级返利，再结算升级**；永久卡不返利 |
| 额外设备 | ≥0（台） | 账号级「可绑定设备」之上多给几台 |
| 额外并发 | ≥0（个） | 账号级「同时在线」之上多给几个设备名额。只抬高上限，**不绕过满员策略** |
| 赠送换绑 | ≥0（次） | 有效免费换绑 = 应用免费次数 + 本值（机器/IP 共用） |
| 状态 | 0 禁用 / 1 启用 | 禁用的等级不参与升级匹配 |

> **默认档**：账号未升到任何等级即默认档，**`level=1`**、返利 0、无额外福利（不落库）。展示名称：**配置了 `level=1` 的启用等级则用其名**，否则显示「默认会员」。
> **累充改动**：后台「编辑账号」直接改累计充值会**按新值重新校准等级**（改高升级、改低降级、归零回免费账号）。
> ⚠️ **等级是全站一套**：在 A 应用充值升级到黄金，在 B 应用也是黄金。

## 五、基础信息与更新策略

> 版本号 / 更新方式 / 下载地址 / 更新公告**不再挂在应用上**，而是存在独立的
> `app_versions` 版本列表里（一应用多版本）。见下方 5.2。

### 5.1 应用基础信息

| 设置 | 字段 | 取值 | 逻辑 |
|---|---|---|---|
| 应用名称 | `name` | 文本 | 必填 |
| 插件标识 | `plugin_id` | 文本（唯一，可空） | 本地插件 ID（如 `com.example.esp`）。填了之后：`72` 权益清单按插件打标；`3 检测最新版本` 传 `plugin_id` 时可据此定位到本应用 |
| 应用状态 | `status` | 0 禁用 / 1 启用 | 禁用后该应用所有接口不可用 |
| 应用数据 | `app_data` | 文本（base64） | 下发给所有用户的公共数据（`42` 读取），单独入口编辑 |
| 程序公告 | `announcement` | 文本（base64） | 随 `1 获取程序公告` 下发，单独入口编辑 |

### 5.2 版本列表（应用 → 操作 → 版本列表）

| 字段 | 取值 | 逻辑 |
|---|---|---|
| 版本号 | 文本（如 `3.0.2`） | 同一应用下唯一；`app_uuid + version` 联合唯一 |
| 更新方式 | 0 不启用 / 1 强制更新 / 2 自由更新 | **强制更新**=版本过旧则**直接拒绝登录**（返回 `code=2` + 更新信息，不发令牌）；**自由更新**=登录成功但提示可更新，用户可不更新；`0` 不下发更新 |
| 下载地址 | URL | 更新方式非 0 时使用；留空表示只提示更新、需手动安装 |
| 更新公告 | 文本 | 走 `2`/`3`/登录 `update` 下发，客户端更新弹窗展示 |
| 启用 | 开关 | **只有启用的版本参与比对**；多个启用时取版本号最高的那条 |

判定规则：

- 更新检查**只读版本列表**，列表里没有已启用的记录 = 「没有可更新版本」，不下发更新信息；
- 登录时若最高版本的更新方式为**强制**且客户端版本更低 → 直接拒绝登录，不核销卡、不建号、不开会话；
- 心跳**不做版本判断**，避免使用中被踢；
- 插件自检更新请用 `3` 的 `plugin_id` 参数（否则会拿插件版本和宿主应用比，必误报）。

## 六、全局账号策略（不在应用里）

这些开关**全站生效**，入口在「账号中心 → 账号策略」。它们产生或消耗的是全局资源，因此不能按应用配置。

### 6.1 卡密登录与充值

| 设置 | 键名 | 取值 | 逻辑 |
|---|---|---|---|
| 卡密登录 | `account_card_login_enabled` | 0 关 / 1 开 | 开启后卡密可直接登录（`10`）；**首次用某卡登录自动建号**（用户名=卡号）并核销 |
| 卡密充值 | `account_recharge_enabled` | 0 关 / 1 开 | 开启后卡密可为已有账号充值（`22`），按卡面值加时长和/或点数 |

### 6.2 账号注册

| 设置 | 键名 | 取值 | 逻辑 |
|---|---|---|---|
| 账号注册 | `account_register_enabled` | 0 关 / 1 开 | 关闭则注册接口直接拒绝 |
| 邮箱验证 | `account_email_verify_enabled` | 0 关 / 1 开 | 开启须先发验证码（`23`）、注册带 `code`。依赖系统 SMTP + Redis |
| 卡密注册 | `account_card_register_enabled` | 0 关 / 1 开 | 开启后注册须额外提交**有效卡密**；注册即核销该卡并按面值发放 |
| IP 限制 | `account_register_limit_enabled` | 0 关 / 1 开 | 按注册 IP 统计，达上限拒绝 |
| 设备限制 | `account_register_device_limit_enabled` | 0 关 / 1 开 | ⚠️ 开启后**注册必须带 `machine_code`**，按注册设备统计；换 IP 绕不过 |
| 限制窗口 | `account_register_limit_time` | 0 每天 / 1 永久 | **IP 与设备两维度共用** |
| 注册次数 | `account_register_count` | ≥1（默认 **3**） | IP、设备两维度**共用同一上限值**（**全站计数**） |

> ⚠️ **注册次数是全站计数，不是按应用**。原因：账号全站唯一，若按应用分别计数，用户在一个应用用完额度后换个应用就能继续注册全局账号，限制形同虚设。
> ⚠️ 因此默认值从 1 调整为 **3** —— 全站计数下填 1 会导致同一 IP 注册过第一个账号后再也注册不了。
> ⚠️ 注册成功**不下发 token**；无试用/卡密时账号**初始即过期**，需再登录/充值/领试用才能用。

### 6.3 领取试用

领取试用是**独立接口（`24`）**，不是注册自动赠送。

| 设置 | 键名 | 取值 | 逻辑 |
|---|---|---|---|
| 领取试用 | `account_trial_enabled` | 0 关 / 1 开 | 关闭或两项额度都为 0 时报「未开启试用领取」 |
| 限制窗口 | `account_trial_limit_time` | 0 每天 / 1 永久 | 每天=每天可领一次；永久=每账号仅一次 |
| 领取方案 | `account_trial_claim_mode` | 0 无限制 / 1 资源耗尽可领 | **无限制**=满足次数即可领；**资源耗尽可领**（默认）=仅「到期已过且点数为 0」才可领 |
| 试用点数 | `account_trial_points` | ≥0 | 发放到点数钱包；0=不发放 |
| 试用时长 | `account_trial_duration_minutes` | ≥0 | 分钟，发放到到期时间；0=不发放。**两项可同时配置** |

> ⚠️ **试用计数全站共享**：一个账号在全站只能领到限额内的量，换应用不可重复领。
> 「资源耗尽可领」的判定同时看两个钱包：到期已过**且**点数为 0。有任一份资源都算「仍可用」。

### 6.4 绑定与转绑

`bindings` 表无 `app_uuid`，一个账号在所有应用共用同一批绑定记录，
额度也只算一份。设备与 IP 是**两套独立额度**：换电脑和换网络是两件事，
共用配额会让「出差连了别的 WiFi」把设备转绑次数吃掉。

| 设置 | 键名 | 默认 | 逻辑 |
|---|---|---|---|
| 设备校验 | `account_machine_verify` | 0 | 0=不校验（不写白名单、不限设备数）；1=激活必须带设备码并受「可绑定设备」约束 |
| IP 校验 | `account_ip_verify` | 0 | 0 关 / 1 精确 IP / 2 同市 / 3 同省；市省级依赖归属地库 |
| 允许设备转绑 | `account_machine_rebind_enabled` | 1 | 关闭时转绑接口报「未开启转绑」 |
| 设备免费次数 | `account_machine_rebind_free_count` | 1 | 本窗口内不扣费；会员等级可额外赠送 |
| 设备计数窗口 | `account_machine_rebind_limit_time` | 1 | 0=每天重置 / 1=永久累计 |
| 设备次数上限 | `account_machine_rebind_max_count` | 0 | **0=不限**；超出后连付费转绑也不允许 |
| 设备超额扣除（分钟） | `account_machine_rebind_deduct_minutes` | 0 | 计时模式下超免费次数后每次扣多少分钟 |
| 设备超额扣除（点数） | `account_machine_rebind_deduct_points` | 0 | 点数模式下超免费次数后每次扣多少点 |
| 允许 IP 转绑 | `account_ip_rebind_enabled` | 1 | 同上 |
| IP 免费次数 | `account_ip_rebind_free_count` | 2 | 换网络比换电脑频繁，默认更宽松 |
| IP 计数窗口 | `account_ip_rebind_limit_time` | 1 | 0=每天 / 1=永久 |
| IP 次数上限 | `account_ip_rebind_max_count` | 0 | 0=不限 |
| IP 超额扣除（分钟） | `account_ip_rebind_deduct_minutes` | 0 | 计时模式下超免费次数后扣多少分钟 |
| IP 超额扣除（点数） | `account_ip_rebind_deduct_points` | 0 | 点数模式下超免费次数后扣多少点 |

**单次转绑的判定链**（`used` = 该账号在该维度已用次数，全站累计）：

```
used < 免费次数              → 免费放行
免费次数 ≤ used < 次数上限    → 扣 deduct（计时扣分钟、点数扣点数，各用各的配置）
（次数上限=0 视为无上限）
used ≥ 次数上限（且 >0）      → 拒绝「转绑次数已达上限」
```

> ⚠️ **次数上限=0 ≠ 不扣费**：不限次数下，超过免费次数后每次仍按 deduct 扣费。
> **防误重绑**：新值 = 当前已绑值时直接放行，**不计次、不扣费**（幂等，避免同设备白扣）。
> 转绑接口**凭账号密码鉴权、不需登录令牌**——设备/IP 对不上、登不进的用户也能转绑（避免死循环）。
> **设备校验关闭时**：登录不写白名单、激活不要求设备码、也不按设备计在线数（没有可靠设备标识就无法去重）。

### 6.5 账号资源配额

| 设置 | 键名 | 默认 | 逻辑 |
|---|---|---|---|
| 可绑定设备 | `account_max_devices` | 3 | 一个账号最多绑定几台电脑；会员等级可加量 |
| 同时在线 | `account_max_concurrent` | 1 | 一个账号最多同时开着几个设备（按设备码去重，跨应用合计） |

> ⚠️ 两项都**不能填 0**，至少 1，否则账号永远进不去。

## 九、常见坑点汇总

1. **「转绑次数=0」是不限次数，但不等于不扣费**——超过免费次数后仍按扣除额扣点/扣时。
2. **「同时在线」「可绑定设备」不能填 0**——至少 1，否则账号永远进不去；会员等级可以在此基础上加量。
3. **`free_mode=1` 下 `expired_at` / `points` 仍存在但不生效**——客户端别拿它判断可用性，一律视为可用。
5. **设备注册限制开启后注册必须带 `machine_code`**，否则直接被拒；且 IP/设备限制共用「限制窗口 / 注册次数」。
6. **注册次数是全站计数**——填 1 意味着同一 IP/设备全站只能注册一个号。
7. **自动离线时长要 ≥ 心跳间隔**，否则用户正常在线也会被判掉线。
8. **注册不自动发时长**——无卡密/试用时新账号初始即过期，属正常，需再充值/领试用。
9. **钱包跨应用共享**——用户抱怨「在 A 花的点怎么 B 也没了」，那是设计；想隔离请用 `free_mode` 让某应用不参与计费。
10. **高级模式必须配等级点数**——不配也能跑（回退默认值），但「等级越高越便宜」的设计意图就落空了。
11. **删除应用不会删账号/卡密/接口**——只清该应用的会话、审计日志、变量、函数。这是一号通的安全边界。
12. **反向代理部署后 IP 类功能依赖 `server.trusted_proxies`**——默认不信任任何代理（取直连对端地址，防 XFF 伪造）；未配置白名单时所有用户被识别为代理 IP：限流误触发、`account_ip_verify` 校验失真、IP 转绑与地区校验失效。直连部署无需配置。
13. **`account_machine_verify=0` 时三件事同时失效**：登录不写设备白名单、激活不要求设备码、不按设备计在线数。想让「可绑定设备 / 同时在线」生效，必须先打开设备校验——没有设备码就无法去重。
14. **设备转绑和 IP 转绑是两套独立额度**：换电脑和换网络分开计次、分开扣费，互不挤占。
